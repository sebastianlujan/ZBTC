# ZBTC v2: research, limits and sources

Date: 2026-10-30. Companion to [codex_plan.md](codex_plan.md). Sources were read only; nothing was executed.

## Conclusion

The sources support a functional, deliberately insecure round trip and nothing stronger. The official toy construction decrypts from ciphertext matrices and a witness, not setup randomness (C01), and the paper's matrix algorithms can be reused for functional recovery without claiming its security guarantees (C04). The rest is unverified or deferred: no complete Circom/Groth16-to-AADP compiler was verified, and exporting R1CS does not encode a verifier into AADP (C05, C06); size and cost figures are format calculations or paper/author estimates, not measurements, and the correspondence between later author revisions and the inspected code is unverified (C02, C07); the challenge tools expose setup secrets (C03); a released key can sign other messages and a public unlock witness can be copied (C08, C09); fixed-signature release still trusts the setup signer (C10); the existing PoC vault is not a PIPE implementation (C11); and the published attacks and the author's patch are background whose evaluation is deferred (C12, C13).

For how PIPEs v2, AADP, Shielded Bitcoin and Shielded CSV relate, and what "private Bitcoin" means (cases A/B/C), see [`../../v1/docs/research.md`](../../v1/docs/research.md) §2 and §5 (Spanish).

## Claims

These observations explain provenance and limits; security findings are not demo acceptance gates. Nothing was executed.

| Claim | Classification | Finding | Sources |
| --- | --- | --- | --- |
| C01 | source observation | The official toy contains setup/encrypt/decrypt. Its valid-witness mode is off by default, uses three secret bits, and encrypts one BN254 scalar-field element. Decryption takes ciphertext matrices and a witness, not setup randomness. | [S01](https://github.com/alloc-init/aadp-cryptographic-challenges/blob/master/code/aadp_construction.sage) |
| C02 | source observation and calculation | The writer serializes a 32-byte target and m matrices of dimension 2m+1. With m=8, the public file is 32+8*17*17*32=74,016 bytes, excluding the proposed AEAD envelope. This is a format calculation, not measured runtime. | [S02](https://github.com/alloc-init/aadp-cryptographic-challenges/blob/master/code/aadp_challenge_writer.sage) |
| C03 | source observation | The challenge tools retain and expose setup secrets. Publishing the original matrix alongside its encrypted version also exposes their plaintext difference. Their outputs require an explicit public/private split for the experiment. | [S01](https://github.com/alloc-init/aadp-cryptographic-challenges/blob/master/code/aadp_construction.sage) [S02](https://github.com/alloc-init/aadp-cryptographic-challenges/blob/master/code/aadp_challenge_writer.sage) |
| C04 | source observation | The AADP security construction uses projectively safe constraints and a tailored SNARK with fixed G2 arguments. The deliberately uncertified toy below reuses its matrix algorithms only for functional recovery; it does not claim those security guarantees. | [S03](https://www.allocinit.xyz/uploads/aadp.pdf) |
| C05 | source observation | snarkjs verifies a pairing involving both proof.pi_a and proof.pi_b, validates proof points, and checks public-input ranges. Exporting a Circom R1CS does not encode this verifier into AADP. | [S06](https://github.com/iden3/snarkjs/blob/master/src/groth16_verify.js) |
| C06 | bounded search result | No complete Circom/Groth16-to-AADP compiler was verified in the inspected official challenge and estimate repositories. The challenge circuit and normalization are specialized; the estimate script counts costs rather than producing a working verifier. | [S01](https://github.com/alloc-init/aadp-cryptographic-challenges/blob/master/code/aadp_construction.sage) [S07](https://github.com/alloc-init/crypto-research-aadp-estimates/blob/master/main.py) [S11](https://github.com/alloc-init/aadp-cryptographic-challenges/tree/master/code) |
| C07 | paper estimate and author report | The AADP paper estimates approximately 338 TB without a full implementation. A September 30, 2026 author interview reports approximately 10 TB and subsequent security revisions, explicitly not a production benchmark. Correspondence between those revisions and the inspected code is unverified. | [S03](https://www.allocinit.xyz/uploads/aadp.pdf) [S05](https://insider.btcpp.dev/p/shielded-bitcoin-and-pipes-facts) |
| C08 | source observation | PIPE v2 releases a signing key once. Afterwards its holder can sign other messages. The setup-correctness proof and proposed MPC do not make this toy an implemented trustless setup. | [S04](https://www.allocinit.xyz/uploads/pipesv2.pdf) |
| C09 | engineering inference | A public proof used as an unlock witness can be copied. A fixed ciphertext cannot discover later transfers, revoke an old witness, or establish the latest chain view. A root must be authenticated through accepted issuance and history. | [S04](https://www.allocinit.xyz/uploads/pipesv2.pdf) [S09](https://www.allocinit.xyz/posts/Shielded-Bitcoin-paper) |
| C10 | engineering inference | Encrypting a signature for one complete SIGHASH_DEFAULT transaction could restrict what the recipient receives to that spend. It still leaves the setup signer able to bypass the mechanism and is an experimental variation, not the PIPE v2 construction. | [S10](https://github.com/bitcoin/bips/blob/master/bip-0341.mediawiki) [S04](https://www.allocinit.xyz/uploads/pipesv2.pdf) |
| C11 | source observation | The inspected shielded-bitcoin-poc has a Circom two-input/two-output circuit and real proof tests, alongside mocked replay tests and a demo vault. Its note-proof layer can be studied separately; that vault is not a PIPE implementation. | [S08](https://github.com/harshjv/shielded-bitcoin-poc/tree/0a715f1efba73821d717ac37f39d95aa76dda995) |
| C12 | source observation | The official cryptanalysis attacks sparse ADP/AADP candidates and the NSS variant. This is background for the educational label, not a requirement to repair the demo or evidence that every revised construction is broken. | [S12](https://www.allocinit.xyz/uploads/aadp-attacks.pdf) |
| C13 | author proposed mitigation | The June 9 author patch proposes denser encoded relations and changed gate handling. Implementing or evaluating that patch is deferred; it is not needed to show the selected functional round trip. | [S13](https://www.allocinit.xyz/posts/commutator-attack) [S05](https://insider.btcpp.dev/p/shielded-bitcoin-and-pipes-facts) |
